# Design process

How to approach the work: user intent and flows, clarity first, layout-first workflow, design systems, review and polish, and working from references and generated UI.

Rules within a section are ordered by how many sources back them. **App UI** marks rules for product screens only, **Marketing** for landing pages and websites only; untagged rules apply to both. Each citation (`author/video timestamp`) links to that moment in the source; full entries are in `references/bibliography.md`.

Contents: User intent and flows · Clarity first · Layout-first workflow · Design systems · Review and polish · References and generated UI

## User intent and flows

- Design the whole journey, not polished screens: treat an app as screens and sequences, and for each screen ask how the user got there and what they need next, making the transitions between small decisions feel natural. UX lives in the flow; map it first, even as rough boxes, because users feel gaps instantly. ([jain/beginner-mistakes 0:39], [jain/learn-ui-in-10-minutes 7:28], [jain/think-like-product-designer 0:23])
- Start from user intent (e.g. a search bar for people who came to search) before styling anything; serve secondary intents too (e.g. browsable listings for users without a destination), and expand functionality only as intent expands. Fonts, colors and icons change aesthetics, not function. ([jain/genius-designer 0:25], [jain/macos-apps 0:49])

## Clarity first

- Make things work and feel clear (well-designed states, flows, a consistent system) before making them beautiful: find the minimum UI that lets content shine, cut headers or background images that do nothing, and skip flashy effects like 3D or smooth-scroll when the goal is an action. Clarity is why users love great products; flair can get in the way. ([jain/genius-designer 0:04], [jain/macos-apps 3:59], [jain/think-like-product-designer 0:34])
- Decide whether the project needs to be good or also interesting; respect users' expectations, and add distinctness through micro-interactions or unique features. Good and interesting are different goals; many businesses only need good. ([jain/awful-to-amazing 0:09], [jain/genius-designer 2:02])
- Evolve, don't overhaul, a layout users have relied on for years. ([jain/spotify-wrapped-redesign 1:11])

## Layout-first workflow

- Wireframe the layout before visual design and nail it before adding animation; start a redesign by assessing hierarchy and cutting elements that don't earn their place. A good layout carries the design; a boring wireframe makes everything after it boring. ([jain/awful-to-amazing 0:30], [jain/finance-dashboard-redesign 0:52], [jain/google-ai-redesign 3:45])
- Try several layout options for a section (around four) before settling. That is how the best option surfaces. ([jain/google-ai-redesign 6:24])
- **Marketing:** Define layout and visual identity separately, and drive the identity from one mood image and the feeling the brand should convey rather than a formula. The same wireframe with a different identity feels completely different. ([jain/vibe-coding-cant-fix 1:46])

## Design systems

- Define spacing, type scale, colors and interaction patterns as a small system (styles, variables, reusable components) and stick to it; size it to the team, and break its rules only deliberately. A system gives an architecture for growth; clarity builds user trust and speed. ([jain/beginner-mistakes 3:24], [jain/genius-designer 4:33], [jain/think-like-product-designer 3:27])

## Review and polish

- Review designs at the real target size on the target device, accounting for browser chrome, to check text size, color and fonts. Zoomed-out canvases lead to oversized type and spacing. ([jain/typography 12:09], [jain/web-design-hacks 6:24])
- Polish many small details rather than hunting for one big change. The gap between good and great is almost never one thing. ([jain/landing-page-levels 7:21])
- **Marketing:** Apply a 5-second test: could someone scrolling for five seconds understand the idea? ([jain/captivating-sections 1:13])
- Tune animation timings by eye in the browser rather than trusting the first values. ([jain/load-animations-code 16:40])
- Before reusing an attractive component from a showcase site such as Dribbble, check it for usability, color and contrast problems. Showcase shots often have contrast and usability issues. ([jain/crucial-ui-elements 0:05])

## References and generated UI

- Work from real, simple product references (e.g. Linear-style product screenshots, as of 2026) rather than busy showcase shots, and study real software for how it handles intent, disclosure and onboarding. Real products show the answers; busy shots hide them. ([jain/dashboard-flaws 4:20], [jain/every-ui-concept 4:24], [jain/google-ai-redesign 2:44], [jain/software-must-lie 4:32], [jain/vibe-coding-pro-ui 0:59])
- Don't accept a generated default layout: decide layout and card design deliberately, since that's where generated UI is weakest, then fix fonts, alignment and color. These are the biggest changes for the least time. ([jain/saas-vibe-code-mistakes 1:22], [jain/vibe-coding-pro-ui 5:06])
- Before generating or building UI, pin down its purpose and intended use and list the specific elements it needs (e.g. a sidebar with icons, a Gantt chart). Concrete context produces far more fitting UI. ([jain/vibe-coding-pro-ui 2:54])
